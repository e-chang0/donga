# PR 리뷰 가이드

## 검토 절차

1. PR의 목적, base/head 브랜치, 변경 파일과 커밋을 읽습니다.
2. 동작·오류 처리·입력 검증·테스트·자동화 권한·문서 일치를 확인합니다.
3. 문제가 재현되는 입력 또는 변경 diff 근거를 찾습니다. 테스트 미실행은 명시합니다.
4. 파일/라인과 `[MUST]`·`[SHOULD]` 태그를 사용해 구체적인 피드백을 남깁니다.
5. 작성자는 수정 커밋 또는 보류 이유를 답변하고, 리뷰어는 변경 diff와 CI를 재확인합니다.
6. 필수 수정 해결 및 CI 성공 후 병합합니다. 승인과 자기 검토를 구분합니다.

## 피드백 형식

| 태그 | 의미 | 처리 |
|---|---|---|
| `[MUST]` | 실행 오류, 보안 문제, 요구사항 위반, 중요한 검증 누락 | 병합 전 수정·재검증 |
| `[SHOULD]` | 유지보수, 가독성, 사용성 개선 권고 | 반영하거나 보류 이유 기록 |

```text
[MUST] 파일:라인 — 문제 요약
근거/재현: 어떤 입력·실행 조건에서 어떤 문제가 생기는가?
영향: 사용자나 자동화에 어떤 결과를 주는가?
수정 제안: 무엇을 변경하고 어떤 테스트로 확인할 것인가?

[SHOULD] 파일:라인 — 개선 권고
이유: 기대하는 개선 효과는 무엇인가?
제안: 구체적으로 어떻게 바꿀 수 있는가?
```

발견된 문제가 없으면 억지로 결함을 만들지 않습니다. `[MUST] 확인 완료`로 필수 수용 기준과 확인 근거를 기록할 수 있지만, 이를 발견·수정한 결함으로 집계하지 않습니다. 취향 차이를 `[MUST]`로 요구하지 않습니다.

## 리뷰 상태와 응답

- `COMMENT`: 질문·제안·자기 리뷰. 병합 승인으로 계산하지 않습니다.
- `REQUEST_CHANGES`: 작성자 외 리뷰어가 중요한 미해결 `[MUST]`를 발견했을 때 사용합니다.
- `APPROVE`: 작성자 외 리뷰어가 필수 기준 충족과 테스트 결과를 확인했을 때 사용합니다.
- 작성자는 `[MUST] 수정: <커밋> / 검증: <결과>` 또는 `[SHOULD] 보류: <이유>`로 답변합니다.
- 코드 변경 후에는 영향받는 테스트를 다시 실행합니다. 이미 성공한 검증을 변경 없이 반복할 필요는 없습니다.

## CODEOWNERS와 개인 과제

[CODEOWNERS](../.github/CODEOWNERS)의 현재 담당자는 실제 저장소 관리자 `@e-chang0`입니다. 기본 브랜치에 이 파일이 있어야 이후 PR의 담당자 결정에 사용됩니다. 파일을 추가한 최초 PR에 대한 자동 리뷰 요청까지 보장하지는 않습니다.

현재는 개인 과제이므로 작성자 외 승인자를 만들 수 없습니다. 자기 리뷰는 제목과 본문에 명시하고 `COMMENT`로 남깁니다. 3개의 서로 다른 PR을 검토한 이력과 타인에게 받은 승인 수를 별도로 기록합니다. 강의가 타인의 PR 리뷰를 요구한다면 별도 실제 협업이 필요합니다.

팀원이 합류하면 아래를 함께 적용합니다.

1. 팀원이 저장소 write 권한을 가지고 있는지 확인합니다.
2. CODEOWNERS에 해당 팀원 아이디를 추가하는 PR을 만듭니다.
3. 보호 규칙의 승인 수를 1 이상으로 설정하고 Code Owner 승인을 요구합니다.
4. 타인의 PR을 읽고 실제 근거에 따른 리뷰를 제출합니다. 자기 리뷰를 타인 리뷰로 바꾸어 표기하지 않습니다.
